Photo Drop: combining B and C into one screen

B's spine and C's switch, in a direction that fixes the two flaws the originals carried. This is the implementation plan only, nothing is built yet. The complete spec lives in design/photo-drop-v4/PLAN-BC.md, and it reuses the token set, motion family, wire format and accessibility rules already fixed in PLAN.md.

Beat from C: the orb docks, it does not vanish

When the server comes up, the 200dp orb scales to 0.2 and slides into a small LIVE badge at the top of the card, in one ViewPropertyAnimator pass. No layout swap, no second view. That single movement is what makes the state change felt rather than read, and it is the piece of C that survives intact.

04 The two flaws, and how they die

B's flaw: Stop in an overflow

An overflow is the one place you cannot put a destructive action, because it is the one place users do not look before their thumb has already moved. Here Stop server is a labelled button inside the sheet, in the bottom third of the screen where the thumb already rests. It is always present when live. It is the same action the foreground notification already exposes, so the app and the shade agree about how to stop.

C's flaw: hold-to-stop, which nobody discovers

C made the biggest target on the phone the destructive one, which forced a long-press guard, which users never find. The fix is to split the two meanings of the orb:

  • When live, tapping the orb copies the link. Copying is idempotent and harmless, so a stray pocket tap on a 200dp target does the safe thing and says so.
  • Stopping is a deliberate, labelled, small-target tap in the sheet, not the orb.

And it confirms only when it matters, using the one honest signal /healthz gives us:

void onStopTapped() {
    if (last.sessions > 0) showStopConfirm();   // inline strip in the sheet
    else                    stopServer();        // nothing in flight, act at once
}

The confirm is an inline strip, not an AlertDialog and not a Snackbar. A snackbar is transient, and the user has already put the phone down and walked away, which is exactly why B's overflow argument and C's long-press argument both lose. The result is a destructive action that is discoverable (unlike C) and guarded (unlike a bare tap). That is the combination neither original had, and it is the reason to combine them at all.

Do not cut this A big tap target that kills an in-flight upload is worse than any visual compromise in this document.

Lean, because there is no AndroidX. BottomSheetBehavior, ViewDragHelper and SpringAnimation are all unavailable, and none is needed.

The sheet is content-driven, not draggable

The sheet has exactly two heights, and which one applies is a function of state rather than of user intent, so there is nothing for a drag gesture to do that state does not already do:

  • peek, 72dp: handle and storage row. Stopped, starting, error.
  • full, 208dp: handle, URL row, Copy, flip, sessions row, Stop server. Live.

Animate between them with an ObjectAnimator on height plus a translationY on the content, around 220ms. That keeps C's "it rises from the bottom when there is something worth showing" and drops the entire drag-gesture problem, which was the single largest cost in C. A draggable handle is an explicit v2, not a v1 requirement.

06 State wiring in MainActivity

render(String) becomes render(Health). pill(String,int,int) becomes applyState(AppState). The three booleans collapse into one enum, and the three button listeners collapse into one dispatcher.

enum AppState { STOPPED, STARTING, ONLINE_LOCAL, ONLINE_TUNNEL, STORAGE_LOW, TERMUX_ERROR }

/** Replaces the btnStart, btnStop and btnQrToggle listeners. */
void onOrbTapped() {
    switch (state) {
        case STOPPED:                          startServer(); break;
        case STARTING:                         break;          // inert, not a dead button
        case ONLINE_LOCAL: case ONLINE_TUNNEL:
        case STORAGE_LOW:                      copyLink(); break;   // safe for pocket taps
        case TERMUX_ERROR:                     showPermissionCard(); break;
    }
}

AppState classify(Health h, boolean permitted) {
    if (!permitted) return AppState.TERMUX_ERROR;
    if (!h.up)      return starting ? AppState.STARTING : AppState.STOPPED;
    starting = false;
    if (h.known() && h.reserve > 0 && h.free <= h.reserve) return AppState.STORAGE_LOW;
    return publicUrl.isEmpty() ? AppState.ONLINE_LOCAL : AppState.ONLINE_TUNNEL;
}

void render(Health h) {
    AppState next = classify(h, Termux.permitted(this));
    if (next == state && !somethingChanged(h)) return;  // no redraw on a no-op poll
    state = next;
    applyState(next);       // band colour and text, orb mode, sheet height, QR
    last = h;
}

07 Ordered change plan

Each step builds and runs on its own. Nothing here is a big-bang rewrite; steps 2 and 3 keep the app shippable while the new layout lands underneath it.

  1. Health.java, add the value class. Build. Nothing consumes it yet.
  2. MainActivity.java, swap render(String) for render(Health), add enum AppState and classify(). Keep the old layout, drive the existing pill from applyState. Build, deploy, confirm zero regression.
  3. StatusStripView.java plus activity_main.xml, replace the header with the band and collapse the ScrollView into the pinned four-zone layout. Stage still holds the old link card, sheet is a stub. Build, deploy, walk all six states.
  4. OrbView.java, both modes and the morph. Wire onOrbTapped(), remove btnStart and btnStop. Build, deploy, confirm start-from-orb and copy-when-live.
  5. Handoff card, domain, mono URL, permanent QR, flip. Delete btnQrToggle and qrBox. Build, deploy, then scan the QR with a real phone at arm's length.
  6. Sheet content, storage row, URL row, Copy, sessions, Stop, inline confirm. Build, deploy, confirm the session guard fires.
  7. First-run checklist and permission card (PLAN.md section 8) inside the stage. Build, deploy.
  8. Accessibility and contrast sweep (PLAN.md section 9) over the built layout.
  9. Cleanup, delete the dead btnUpload/btnScan/tvScan wiring and the unreferenced surface_press/row_press/track_bg colours.

What this plan deliberately deletes

  • btnScan, which points at the identical URL as btnOwner. One Owner dashboard row.
  • The hardcoded "No uploads in this session yet" literal, replaced by the real sessions count.
  • The QR toggle. The QR is permanent when live, which was B's whole argument.
  • The ScrollView. Nothing should need scrolling to be seen.

08 Verification, and the cut order

bash apps/photo-drop/android/build.sh      # must print BUILD_OK
bash apps/photo-drop/deploy.sh             # adb install and push to the Samsung
  1. Cold start, stopped. Band grey "Server is offline", the orb is the only large object, sheet is a bare storage peek.
  2. Tap the orb. Band amber, orb amber, no Toast.
  3. healthz answers. Band solid green, the orb shrinks and docks to the LIVE badge, the card fades in with the QR, the sheet grows to full.
  4. Stand back and scan. A second phone scans from about 40cm, in daylight. Real hardware, not a screenshot. This is the test B exists for.
  5. Pocket-tap safety. Tap the orb repeatedly while live. It copies. The server does not stop.
  6. Stop with sessions in flight. The confirm strip appears, not a dialog. With zero sessions the first tap stops at once.
  7. Storage low. Band red, QR withdrawn, alert card in its place.
  8. Revoke the Termux permission. The permission card replaces the orb and persists.
  9. Reduced motion. adb shell settings put global animator_duration_scale 0, confirm the shimmer is stopped rather than spinning, then reset to 1.
  10. Contrast sweep over the built layout. Body text at 4.5:1 or better, QR stays black on white.

Risks, and what to cut first

This is more work than direction A, and it should be said plainly. The orb morph and the sheet both need real animation code, and verification step 4 depends on hardware. Cut in this order if it runs long:

  1. Sheet transition. Show and hide instead of animating height. Keeps both contents.
  2. Orb morph. Swap VISIBLE and GONE between orb and badge, no scale pass. Loses the felt change, keeps the layout.
  3. Pull Stop up beside the card as a labelled button and drop the sheet. This degrades toward B with a permanent QR, which is still a good app.

Never cut The section 4 guard. Everything else is negotiable.

09 Open questions

  1. Live orb. Dock it as a small badge in the card header, as drawn, or fade it out and let the band's LIVE pill carry the state alone?
  2. Does sessions > 0 justify a confirm? It is a proxy for "an upload is in flight", not a guarantee. The alternative is to confirm only below the reserve and stop immediately otherwise.
  3. Drag to expand the sheet. Worth a v2, or is the content-driven two-position sheet enough indefinitely?
  4. The flip. Is a URL-large and QR-large flip wanted, or is the QR always large with the URL as its second line, as drawn?
