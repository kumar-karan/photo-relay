Photo Drop — architecture

A photo drop server that runs inside Termux on the owner's Samsung phone. A friend opens a secret link in a phone browser, picks photos, watches them upload, and the files land in DCIM so Google Photos backs them up to the owner's account. Nothing is installed on the friend's phone.

887 lines of server, 345 lines of shell, 24 tests. Everything below is drawn from the code as it stands, not from intent.

What I added

not available off the shelf

Seven pieces. Each exists because the generic options fail the MediaStore requirement or the space requirement, and I could not verify that until I ran them.

Raw body upload protocol

One file per request, sent as the request body rather than multipart. Removes a parser dependency and, more usefully, Content-Length arrives before any bytes, so a hopeless upload is refused without writing it.

Two phase space guard

Checked from Content-Length up front, then again every 8 MiB during the write. A 4 GB video cannot quietly consume the reserve.

Atomic staging

Write to a hidden .part, then os.replace into place only on success. Rejections leave zero bytes. Stale .part files are swept at boot.

MediaStore ladder

Four techniques tried in order, first success wins, and the winner is reported to the owner dashboard. This is the part no generic file server has.

Server side session store

The cookie is looked up, not compared to the master token. It also gives batches a real owner, which is what makes the file cap meaningful.

Batch ownership

Each batch records the session that created it. Another session gets 403, and the per session cap cannot be reset by inventing a new ?batch=.

Growth caps

Manifest and log are capped and rotated. Both live in Termux home, a different volume from DEST, so a separate free space check covers them.

Confirmation page

Thumbnail grid plus file list, so the friend has evidence rather than a promise. This is where the XSS lived.

Request lifecycle

one file
  1. Friend opens /d/<token>/. No cookie yet, so the token in the path is compared with hmac.compare_digest. A session id is minted, registered server side, and returned as an HttpOnly cookie.
  2. Browser polls /status every 5s for free space. The space bar on the page is driven by a number the server sends, not a guess in the client.
  3. Friend picks files. Queue is client side, nothing uploaded yet.
  4. One POST /upload?batch=&name= per file, raw body. upload.onprogress drives the percentage. This is why the number is honest.
  5. Server checks Content-Length against the cap and against free space minus reserve. Too big is 413, no space is 507. Neither writes a byte.
  6. Stream to .<name>.part in 256 KiB reads, rechecking free space every 8 MiB.
  7. os.replace into DCIM/GuestUploads on success. On any failure the .part is unlinked.
  8. Scan ladder runs. First technique that works is recorded as scanned in the manifest.
  9. Manifest append. Capped at 1 MB, recycled past that.
  10. Friend lands on /done/<batch> with thumbnails, total size, and a warning if any scan failed.

MediaStore ladder

the risky part

Google Photos queries MediaStore, not the filesystem. A file sitting in DCIM is invisible to it until MediaProvider is told the file exists. This is why PairDrop, croc, and every generic file server fail at the last step.

Space guard

fail clean, never fill

A phone that fills up becomes a brick, not a slow uploader. Every path out of this machine ends in a refusal, never a partial write.

507  reserve exceeds free space            no bytes written
507  home partition low                  manifests and logs live there, not in DEST
413  file over the per file cap          no bytes written
507  free space dropped mid write        .part unlinked, nothing survives
409  session file cap reached            counted across all of the session's batches

Reserve default 2 GiB. Tunable via PHOTO_DROP_RESERVE_BYTES.
Why a reserve at all. Without a floor, the last upload wins and the phone dies holding a directory it cannot flush. The friend sees a clean "storage is full" instead of a transfer that stalls at 99 percent forever.

Security model

after adversarial review

One secret, no second factor. Everything below is about not losing that secret and not letting one uploader reach another's data.

The credential

token
24 char random in the URL path, the entire secret
compare
hmac.compare_digest, constant time
session
minted on first visit, looked up server side
cookie
HttpOnly, SameSite=Lax, Secure when proxied
owner
/owner/<token> path form, not a query string

Fixed after review

  • XSS in the confirmation page. Original filename was raw; now escaped. Two independent reviews found the same line.
  • Cookie was decorative. Compared against the master token, could never match.
  • File cap bypass by changing ?batch=. Now per session with ownership markers.
  • /healthz leaked device path, exact free bytes and session counts to anyone.
  • Secure flag silently dropped because Flask sees HTTP behind the tunnel.
  • Unbounded manifest and log on a volume nothing was checking.
Accepted, not fixed. threaded=True allows unbounded concurrent uploads. Every upload route needs the token, so exploitation requires already holding the credential, and adding gunicorn to a Termux install risks a new first run failure. Tracked as a deliberate trade, not an oversight.

Every one of them fails on the same axis. They write files to a directory. This has to write files to a directory and convince Android's media database they exist. That second half is 112 lines of shell here and zero lines anywhere else.

Open risks

unknown until the phone answers

MediaStore ingestion

Unverified. No Android device has been attached this session. The ladder reports which rung works so this resolves on first upload rather than staying a guess.

Tunnel handshake

Unverified. --protocol http2 --edge-ip-version 4 is set to dodge Android's resolver, per a known cloudflared issue. Never run against a real tunnel here.

First run failure

Three already found and fixed by review: an invented package name, the glibc binary, and PEP 668. Each would have stopped the install dead.
